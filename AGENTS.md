# IntentSignal — Paid Ads Lander (Retainer)

Static site in **this folder only** (this is the **git repo root** for [is-paid-ads-lander-retainer](https://github.com/elsakra/is-paid-ads-lander-retainer)).

- **Entry**: `index.html` (drafts: `index v1.html`, `index v2.html`). Canonical/OG domain is **`go.intentsignal.ai`**; social card is `assets/og-card-v2.png` (1200×630, regenerated with the hero copy — bump the `-vN` suffix if the hero claim changes, since `/assets/**` is immutably cached).
- **Hero claim**: H1 is **"30 qualified meetings a month. Per client."** — a checkable number, and the first thing a prospect will test on the call. It is stated again in the subhead as a 2026 average, and mirrored in `<title>`/OG/meta. If the number moves, change it in all five places plus the social card.
- **Paid ads**: the subhead claims **cold email and paid ads**. That claim is supported in two places below the fold — the "Two channels, one pipeline" card in *What you actually get*, and a comparison row. Do not remove the subhead mention without removing those, or vice versa; a dangling channel claim is worse than none.
- **Stack**: HTML + Tailwind CDN, `assets/`. Deploy: push **`main`** → Vercel. `vercel.json` sets long `Cache-Control` for `/assets/**` (bump filename or query if you need to bust a cached asset). Do not commit **`.vercel/`** (gitignored) or anything under **`uploads/`** (gitignored; scratch assets only).
- **Qualifier**: REMOVED (Aug 2026, paid-traffic prep). The ACV/TAM widget and its yes/maybe/no routing are gone — with paid traffic, nothing on this page disqualifies a visitor. Do not reintroduce a gate without a deliberate decision; a fit test whose every branch books a call reads as theater.
- **Calendly**: ONE destination for every CTA — `https://calendly.com/meetktr/intro-calls-website` (Kyle, 30 min). The five nav/body CTAs open a **popup** via `openCal(el, location)` so the visitor never leaves the domain; the final CTA is an **inline embed** (`.calendly-inline-widget`). `widget.js`/`widget.css` load once from `<head>`. Every CTA keeps a real `href` so it degrades to a plain link if the widget fails. The old David/Kyle rep routing is gone.
- **Conversions**: GA4 `G-HMXSGLFCMW` is the only tag — no `AW-` tag; Google Ads imports the conversion from GA4 property 534312459. The conversion event is **`generate_lead`**, fired two ways: on `/thanks` (page load) and by the parent-window `message` listener in `index.html` on Calendly `event_scheduled`. The listener also redirects to `/thanks` — the Calendly-side redirect is only a fallback, since a popup redirect lands inside the iframe. Only ever listen for `event_scheduled`: Calendly also emits page-view events, and `/api/slack-notify` has no rate limiting.
- **`/thanks`** (`thanks/index.html`): post-booking page, `noindex`, no CTA. Uses **absolute** asset paths (`/assets/...`) since it lives one level down. Its `<head>` duplicates the lander's Tailwind config and fonts — there is no build step to share them, so changes to the palette must be made in both files.
- **Slack notifications**: every Calendly click calls `notifyCalRedirect('kyle', location)` (rep is always `kyle` now; the endpoint just capitalizes whatever it gets) in `index.html`, which `sendBeacon`s `/api/slack-notify`. That endpoint is a Vercel serverless function in `api/slack-notify.js`. Webhook URLs are NEVER placed in HTML/JS — they live only in Vercel → Project → Settings → Environment Variables (Production + Preview). **Two channels**: clicks go to `SLACK_WEBHOOK_URL`; confirmed bookings (`location === 'booked'`, fired by the `event_scheduled` listener) go to `SLACK_BOOKINGS_WEBHOOK_URL`. If the bookings var is unset it falls back to `SLACK_WEBHOOK_URL`, so a missing env var degrades the channel rather than dropping the notification.
- **Booker details in the booking alert**: Calendly's `event_scheduled` postMessage carries **only URIs**, so the name/email are fetched server-side. `index.html` forwards `payload.invitee.uri`; `fetchInvitee()` in `api/slack-notify.js` GETs it with `CALENDLY_API_TOKEN` (Calendly personal access token, Vercel env) and `describeInvitee()` renders name, email, the three intake answers (Company Name / Job Title / biggest challenge), phone, timezone, Calendly `tracking`, and reschedule/cancel links. **The invitee URI comes from the browser and is therefore untrusted** — `INVITEE_PATH` pins the fetch to `https://api.calendly.com` on the exact `/scheduled_events/{uuid}/invitees/{uuid}` path so the endpoint cannot be used as an open proxy. Do not relax that check. Without the token the alert still fires, just without the booker block.
- **Calendly-side tracking**: `calTrackingQS()` appends `utm_*` to the popup URL so Calendly records them in its own `tracking` object (visible in the Calendly UI and API, not just Slack). A Google Ads click id is mapped to `utm_source=google&utm_medium=cpc`, since Calendly has no gclid field.
- **Booking attribution**: `captureAttribution()` in `index.html` stores **first-touch** `gclid`/`gbraid`/`wbraid`, `utm_*` and `document.referrer` in `sessionStorage` under `is_attr` on landing (first touch wins; it survives the Calendly popup and the `/thanks` redirect). `describeSource()` in `api/slack-notify.js` turns that into the booking message. **A Google Ads click id is the only thing that claims Google Ads** — utm-only traffic is reported by its source, referrer traffic by hostname, and everything else as direct/unknown. Do not default the message to "Google Ads": this lander also takes direct and organic traffic, and a booking notification that misattributes its source is worse than none. If a booking says "direct / unknown" and you expected Ads, the likely cause is auto-tagging off in Google Ads or a redirect stripping the query string.
- **Logo walls** (`index.html`): Primary strip **Trusted By** and the meetings **marquee** use `loading="eager"` and `decoding="async"` (not `lazy`—logos are above the fold). Header lockup has `fetchpriority="high"`; the duplicate marquee copy uses `fetchpriority="low"`. `link rel=preload` for the lockup and first marquee image (currently `aarp.png` — move the preload if the strip is reordered). **The marquee renders two identical sets on purpose**: the `translateX(-50%)` keyframe needs both to loop seamlessly, the clone is `aria-hidden` with empty `alt`, and `prefers-reduced-motion` hides it. Do not "deduplicate" it. Clay uses `clay-v2.avif` (4.8 KB); the old `clay.png` was 961 KB and was the heaviest asset on the page. **Meetings** marquee (~28s loop; `prefers-reduced-motion` disables scroll). `mark-mono` + `mark--from-white` (all-white assets) + `mark-on-light` (Alignops in the hero). **Rocket Lawyer** is not in the meetings strip. **McDonald’s** and **Disney** in the meetings strip use path-based wordmarks: `assets/logos/recent-2026/mcdonalds-wordmark.svg` and `disney-wordmark.svg` (sourced from Wikimedia Commons; trademark remains with the rights holders). **Turo** is not in the strip. Case study Route: `client-logo--case`. Assets: `assets/logos/`, `assets/logos/recent-2026/`, `assets/logos/clients/`.

## Meetings on Demand (`/ondemand`)

Productized, no-call, **pay-per-held-meeting** offer aimed at Meta ad traffic. Separate pages, same repo/brand/deploy, sharing assets and the `main` → Vercel pipeline. **Reference assets with absolute paths** (`/assets/...`) since pages live under `/ondemand/`.

Model (locked): minimal-friction card capture, then onboard, then deliver and charge on held. **No setup fee, no free meeting, no charge today.** The card is saved at $0 via Stripe Checkout `mode=setup`; the only charge ever is the bid per held meeting. Risk reversal = "no charge today, pay only when a meeting is held." Commitment before work: capture card first, onboard second.

- **Pages**: `ondemand/index.html` (proof + risk reversal + VSL + how-it-works + a one-field checkout: bid only; no eyebrows), `ondemand/onboarding/index.html` (post-payment: booking link, ICP, min-minutes, do-not-contact CSV upload), `ondemand/admin/index.html` (internal ops dashboard), `ondemand/success/index.html` (orphaned fallback; success now routes to onboarding).
- **Funnel**: ad → `/ondemand` → set bid → Stripe Checkout (`mode=setup`: saves card off_session, $0 charge) → `success_url` = `/ondemand/onboarding?cs={CHECKOUT_SESSION_ID}` → onboarding gated on the session being completed/paid → ops builds + charges per held meeting.
- **Pricing**: bid-based, **$200 floor** per held meeting (enforced client-side AND in `create-checkout.js`/`charge-meeting.js`). No setup fee and no charge at signup. The only charge ever is the bid, off_session, per held meeting, fired from the admin console.
- **Stripe (no SDK, native `fetch` to `api.stripe.com/v1`)**:
  - `api/create-checkout.js`: Checkout Session `mode=setup` (saves card off_session, $0 charge), collects email/phone. Returns `{ url }`. Validates bid ≥ $200.
  - `api/stripe-webhook.js`: signature-verified (`STRIPE_WEBHOOK_SECRET`, `node:crypto`, raw body). On `checkout.session.completed`: sets saved card as `invoice_settings.default_payment_method`, stamps bid/email on the customer, and upserts `od_accounts` in Supabase. Point a Stripe webhook at `/api/stripe-webhook` for `checkout.session.completed`.
  - `api/charge-meeting.js`: **admin-only** (`x-draw-secret: $ADMIN_DRAW_SECRET`). Off_session PaymentIntent for the bid against the saved card, per verified-held meeting. Logs to `od_meetings`. On card failure → 402 + Slack alert.
  - `api/onboard.js`: verifies the session is paid, then writes config to `od_accounts` and uploads the CSV to Supabase Storage (`od-blocklists` bucket).
  - `api/admin-accounts.js`: admin-only read of `od_accounts` + `od_meetings` for the dashboard.
- **Supabase** (project `intentsignal-tools`, ref `pcnxfjylnibxxdkhkvxz`, URL `https://pcnxfjylnibxxdkhkvxz.supabase.co`): tables `od_accounts`, `od_meetings` (public schema, `od_` prefix, RLS on with no policies — only the service-role key touches them), private storage bucket `od-blocklists`. Migration: `meetings_on_demand_schema`.
- **Env vars** (Vercel → Settings → Environment Variables, Prod + Preview; NEVER in HTML/JS): `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `ADMIN_DRAW_SECRET`, `SUPABASE_URL` (`https://pcnxfjylnibxxdkhkvxz.supabase.co`), `SUPABASE_SERVICE_ROLE_KEY`, plus existing `SLACK_WEBHOOK_URL`. Without keys the page still renders and the checkout button shows a graceful "not live yet" message.
